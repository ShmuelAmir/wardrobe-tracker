# Research: Convex Free-plan ceilings — does egress actually bind?

Ticket: [ShmuelAmir/wardrobe-tracker#89](https://github.com/ShmuelAmir/wardrobe-tracker/issues/89)

Date: 2026-08-07

Scope: wardrobe-tracker is replatforming to a Convex-backed web app + PWA (#87), single private user, **Free tier only** (hard constraint). Provisioned deployment: Convex 1.43.0, region eu-west-1, plan Free. Storage is not the constraint (1 GB ≈ 6–7k items at ~150 KB each); this ticket judges whether **egress** (1 GB/month) and the **function-call / database-I/O** ceilings bind for a reactive image-grid app, and quantifies where the real line is.

All figures below are the Free-plan monthly ceilings established in #88 and re-confirmed verbatim against the current limits/pricing pages: 1M function calls, 20 GB-hours action compute, 0.5 GB database storage, 1 GB database I/O, 1 GB file storage, 1 GB data egress, 0.5 GB search storage, 3,000 query-GB search queries, 40 deployments.

---

## Verdict (up front)

**Egress is real but not automatically fatal — it depends entirely on whether the app sets strong `Cache-Control` headers itself.** Convex's own docs never mention a CDN in front of file storage and never document a default `Cache-Control` header on `storage.getUrl()` links; a third-party engineering writeup that hit this exact problem found the **default storage response is not cached like "a strong public immutable asset"** and had to build a custom HTTP-action route with explicit `public, max-age=1y, immutable` headers to fix it [tigerabrodi.blog]. Convex file URLs generated by `getUrl()` *are* stable/non-expiring bearer URLs (revoked only by deleting the file, never by time) [docs.convex.dev/file-storage/serve-files], so they are technically cacheable — but nothing in Convex's own material guarantees the browser will actually cache them well by default.

Given that, a single user with a ~200-item grid (~30 MB fully uncached) crosses the 1 GB/month egress ceiling in roughly **33 uncached full-grid loads** — trivially reachable within a month of casual multi-visit-per-day use *if the app doesn't explicitly set long-lived cache headers on image responses*. With deliberate strong caching (serve images through a custom HTTP action with `Cache-Control: public, max-age=31536000, immutable`, matching the workaround in [tigerabrodi.blog]), repeat views cost **zero** egress because the browser never re-requests the bytes, and realistic monthly egress collapses to roughly "cold first load + newly added/edited item images" — well under 1 GB for a single-user 200-item wardrobe. **The engineering conclusion: do not rely on Convex's default file-serving behavior; wardrobe-tracker must explicitly configure long-lived, immutable cache headers on image URLs (custom HTTP action, not raw `getUrl()` in an `<img>` tag) to keep egress inside the Free plan.**

Function calls and database I/O are not a binding constraint for this app at any realistic single-user scale (see §3).

## 1. How Convex serves files: CDN, headers, URL stability

**Documented:**
- Files are served by generating a URL from `storage.getUrl()` (in a query/mutation/action) and rendering it directly in `<img src>`. This is Convex's primary documented pattern. [docs.convex.dev/file-storage/serve-files]
- These URLs are **bearer URLs, not signed/expiring**: "anyone with the URL can access the file" without further app authorization, and "the only way to revoke a file URL is by deleting the file" — there is no automatic expiry. [docs.convex.dev/file-storage/serve-files]
- The alternative path — serving via a custom HTTP action (`ctx.storage.get()` returning a `Response`) — exists specifically for per-request auth checks, and is capped at a 20 MiB response size. [docs.convex.dev/file-storage/serve-files]
- Convex explicitly points users wanting **expiring** URLs to the third-party Cloudflare R2 component, implying native file storage URLs are intentionally *not* time-limited. [docs.convex.dev/file-storage/serve-files]

**Not documented (silent):**
- Whether a CDN sits in front of `*.convex.cloud`/`*.convex.site` file responses.
- What `Cache-Control` header (if any) is set by default on a `getUrl()` response.
- Any geographic/edge distribution behavior.

**Inferred (secondary source, not Convex-owned):** an engineer who hit slow/uncached Convex storage assets in production found the built-in storage response "was not behaving like a strong public immutable asset," and fixed it by adding a **custom HTTP route inside Convex** that reads from storage and re-serves the bytes with `Cache-Control: public, max-age=<1yr>, s-maxage=<1yr>, immutable` set manually. This implies the default response either omits strong cache directives or is not reliably CDN-cached — enough that a production user needed to hand-roll it. [tigerabrodi.blog — secondary/community source, not confirmed by Convex]

**Conclusion for this question:** URLs are stable and cacheable in principle (no signing/expiry to fight), but Convex does not document — and available evidence suggests it does not provide by default — the strong cache headers needed to actually keep egress off the metered path. This must be built explicitly (custom HTTP action + explicit `Cache-Control`), not assumed.

Sources:
- https://docs.convex.dev/file-storage/serve-files
- https://docs.convex.dev/file-storage
- https://tigerabrodi.blog/how-i-fixed-slow-convex-storage-assets-with-convex (secondary; corroborating evidence only, not a Convex primary source)

## 2. Does egress metering count cache hits, or only origin fetches?

**Unknown / undocumented.** The limits page defines file "Data egress" only as: **"Includes serving user files, accessing user files inside functions, and generating and restoring backups."** [docs.convex.dev/production/state/limits] There is no language anywhere in the pricing or limits pages distinguishing a CDN/edge cache hit from an origin fetch, because Convex's docs never assert a CDN exists in front of file storage in the first place (§1).

What *can* be said with confidence, based on plain HTTP semantics rather than Convex-specific documentation: a **browser cache hit never leaves the client**, so it can never be metered as Convex egress regardless of how Convex's backend accounting works — the request simply isn't made. The open question is not "does Convex bill cache hits" but "does Convex make it easy for the browser to actually have a cache hit," and §1 shows the answer is "only if you configure it yourself."

Sources:
- https://docs.convex.dev/production/state/limits ("File Storage" table, Data egress row)
- (browser caching behavior itself is standard HTTP, not a Convex-specific claim)

## 3. Do the 1M function-call / 1 GB database-I/O ceilings constrain a reactive image grid?

**Documented, and the answer is no — not at single-user scale.**

- **What counts as a function call is explicit:** *"Explicit client calls, scheduled executions, subscription updates, and file accesses count as function calls."* [docs.convex.dev/production/state/limits, Functions table] So yes — every time a subscribed query re-runs because underlying data changed, that re-run is billed as one function call, same as an explicit call.
- **How re-runs are triggered:** Convex tracks "all of the documents a query reads from the database, and re-running the query when any of them change" [stack.convex.dev/queries-that-scale] — i.e., a subscription only re-executes on a relevant write, not on a timer or on every render.
- **Query result caching exists and reduces load for *shared* queries:** "Convex caches query results automatically. If many clients request the same query, with the same arguments, they will receive a cached response." [stack.convex.dev/queries-that-scale] This benefit is largest for multi-client apps; for a single private user it mostly matters if the same query is open in two tabs/devices simultaneously.
- **Database I/O** is separately defined as "Document and index data transferred between Convex functions and the underlying database" [docs.convex.dev/production/state/limits, Database table] — this is about the *document rows* a query reads (e.g., item metadata: name, category, storage ID), not the image bytes themselves (images are served via file storage and metered under file egress, §1–2, not database I/O).

**Quantifying it:** for a single-user wardrobe app, mutations (add/edit/delete item, mark worn) are human-paced — at most a few dozen per day of active use. Each mutation triggers at most a handful of dependent query re-runs (e.g., the wardrobe-grid query, a stats query). Even a generous 100 mutations/day × 5 dependent re-subscriptions = 500 function calls/day ≈ 15,000/month, **1.5% of the 1M ceiling.** Each re-run reads item *metadata* documents, not images — a 200-item table of small JSON-like records (well under 1 MiB per the document-size limit) means a full re-scan is on the order of tens of KB, not MB. Even hundreds of full re-scans per month stay orders of magnitude under the 1 GB database-I/O ceiling. Neither ceiling is a realistic constraint for this app; egress (§1–2, §4) is the only one that plausibly binds.

Sources:
- https://docs.convex.dev/production/state/limits (Functions table: "count as function calls"; Database table: I/O definition)
- https://stack.convex.dev/queries-that-scale (dependency-tracked re-run mechanism; query result caching)
- https://docs.convex.dev/realtime (general reactivity: "Convex tracks the dependencies to your query functions... and triggers the subscription in the client libraries")

## 4. At what point does a realistic single user cross 1 GB/month egress?

**Baseline arithmetic (already established in #88, restated for context):** 200 items × ~150 KB/normalized image (per ADR-0006) ≈ 30 MB for one fully-uncached grid render.

**Worst case — no effective caching** (default behavior is undocumented/unconfirmed to cache well, §1):
- 1,024 MB ÷ 30 MB/load ≈ **~34 uncached full-grid loads** exhausts the month.
- A single user opening the wardrobe app a few times a day, on a device/browser combination where images aren't being served from disk cache (weak or absent `Cache-Control`, private/incognito browsing, frequent cache eviction, or a second device), could plausibly hit 34 "cold" grid renders well inside 30 days — e.g., **5 uncached opens/day blows the monthly budget in under a week.**

**Realistic case — strong caching configured** (custom HTTP action + `Cache-Control: public, max-age=1y, immutable`, per §1's documented fix pattern):
- First load of the full grid on a given device: ~30 MB, one time.
- Every subsequent view of an *unchanged* item's image: 0 bytes of egress (served from browser disk cache, never reaches Convex).
- Ongoing monthly egress ≈ (bytes of *newly added or edited* item images that month) + (any additional "first loads" from a new device/browser profile/cleared cache).
- For a personal wardrobe growing at a modest pace (say 10–20 new/edited items/month × 150 KB ≈ 1.5–3 MB) plus occasional re-cold-loads (new phone, cleared cache, second device ≈ another 30 MB event), realistic monthly egress lands in the **tens of MB**, roughly **3–5% of the 1 GB ceiling** — not close to binding.

**The crossover condition, stated plainly:** the 1 GB egress ceiling is crossed by *repeated uncached fetches of the same images*, not by wardrobe size or by normal single-user growth. It binds under: no explicit long-lived cache headers (default behavior only, §1), frequent visits, multiple devices/browsers without persistent cache, or synthetic/testing traffic (e.g., repeated dev-mode reloads, QA passes) — all of which are plausible during development and initial usage of this exact app.

Sources:
- https://docs.convex.dev/production/state/limits (1 GB/month egress ceiling; arithmetic in this section is derived from that figure plus #88's 150 KB/200-item baseline, not an independent Convex claim)

## 5. What happens when a ceiling is hit on the Free plan?

**Documented, staged, non-destructive — but not silent either:**

1. **Warning stage:** *"Convex sends notification emails as you approach a resource limit."* [convex.dev/pricing/faq]
2. **Sustained-overage stage:** *"If you exceed the resource limit for an extended period of time, your deployment may return HTTP errors in response to function calls."* [convex.dev/pricing/faq]
3. **Specifically for database writes:** *"After these limits are hit on the Free plan, new mutations that attempt to commit more insertions or updates may fail."* [docs.convex.dev/production/state/limits]
4. **No automatic upgrade and no stated data loss.** The Free plan is explicitly described as having **"hard resource caps,"** in contrast to Starter, which "can exceed its included resource amounts with usage-based pricing" [docs.convex.dev/production/state/limits]. Free does not silently convert to pay-as-you-go — a human has to explicitly move to Starter (the first paid tier) to lift the cap. Existing stored data is not described as being deleted or corrupted by hitting a limit; the failure mode documented is functional (calls/mutations erroring), not destructive.

**Not documented:** the exact HTTP status code(s) returned, how "an extended period of time" is defined, whether reads (queries) are affected the same way as writes (mutations), and whether file-serving specifically (as opposed to function calls generally) degrades gracefully or hard-fails once the 1 GB egress ceiling is crossed mid-month. Treat "queries/image-serving still work but mutations fail" as the documented floor, not a confirmed complete picture.

Sources:
- https://www.convex.dev/pricing/faq
- https://docs.convex.dev/production/state/limits

## Conflicts / uncertainties

- The single most load-bearing fact in this ticket — whether Convex file storage sits behind a CDN and what its default cache headers are — is **not stated anywhere in Convex's own documentation**. The one piece of evidence found (a third-party blog post) is second-hand and could be outdated or specific to that author's setup; it should be treated as a strong hint to build explicit caching, not as ground truth about current Convex infrastructure.
- Whether "extended period of time" (§5) means hours or days is undefined, so the practical blast radius of a mid-month egress overrun (e.g., does image serving itself get throttled, or only mutations) is not fully confirmed.
- The arithmetic in §4 assumes the ADR-0006 ~150 KB/image figure and #88's 200-item baseline; it was not independently re-derived here.
